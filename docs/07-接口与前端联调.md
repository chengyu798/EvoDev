# 接口与前端联调

## 1. 实现目标

Web 控制台负责完成一条可演示的主路径：用户用自然语言描述代码问题，并关联本地 Git
仓库；后端立即创建运行并继续执行多智能体修复；前端持续查询状态，在运行结束后展示测试、
智能体、代码差异和经验证据。

界面采用“历史对话侧栏 + 对话式任务区 + 结构化证据区”的混合结构。创建页面把问题描述
作为主要输入，任务名称可以根据描述自动生成；测试命令、最大修复次数与修改约束收纳在运行
设置中。运行详情先串联用户任务和 EvoDev 响应，再展示工作流、执行摘要、测试报告、智能体
轨迹、代码变更和经验记录。页面默认进入新任务输入，历史任务仅在用户主动选择时打开。整体
使用暖白、日光黄和低饱和暖灰组成的明亮主题。

任务与运行摘要保存在 PostgreSQL，避免后端重启后列表丢失。体积较大的测试日志、工具轨迹
和补丁继续保存在 `outputs/<run_id>/`，避免把大段文本重复写入运行表。

## 2. 接口清单

| 方法 | 路径 | 中文用途 |
|---|---|---|
| `GET` | `/api/health` | 查询后端和 Docker 沙箱状态 |
| `POST` | `/api/tasks` | 校验并创建修复任务 |
| `GET` | `/api/tasks` | 查询任务列表 |
| `GET` | `/api/tasks/{task_id}` | 查询单个任务 |
| `POST` | `/api/tasks/{task_id}/runs` | 创建后台运行并立即返回 `202` |
| `GET` | `/api/runs` | 查询最近运行 |
| `GET` | `/api/runs/{run_id}` | 查询当前状态和指标摘要 |
| `GET` | `/api/runs/{run_id}/events` | 查询 LangGraph 节点事件 |
| `GET` | `/api/runs/{run_id}/artifacts` | 聚合本次运行已经产生的复查文件 |
| `POST` | `/api/runs/{run_id}/cancel` | 请求取消未结束运行 |

## 3. 任务创建字段

| 字段 | 中文含义 |
|---|---|
| `repository_path` | 宿主机上的本地 Git 仓库绝对路径 |
| `issue_title` | 任务名称；前端留空时根据问题描述自动生成 |
| `issue_body` | 预期行为、当前问题和验收条件 |
| `test_command` | Docker 沙箱内执行的 pytest 命令 |
| `constraints` | Agent 修改代码时必须遵守的约束列表 |
| `max_iterations` | 最大自动修复次数，可选 1 至 3 |

仓库路径必须存在并包含 `.git`。系统只把原仓库复制到
`.evodev/workspaces/<run_id>/`，所有代码修改都发生在该隔离工作区。

## 4. 运行摘要字段

| 字段 | 中文含义 |
|---|---|
| `status` | 当前运行状态 |
| `current_node` | 最近完成或正在展示的工作流节点 |
| `iteration` | 已进入 Developer 的次数 |
| `tests_passed` | 修改后测试是否通过 |
| `review_passed` | Reviewer 是否通过补丁 |
| `changed_files` | 隔离工作区中的修改文件 |
| `retrieved_experience_ids` | 本次运行使用的历史经验编号 |
| `generated_experience_id` | 失败运行新生成的经验编号 |
| `retry_count` | 自动重试次数 |
| `prompt_tokens` | 模型输入 Token 数量 |
| `completion_tokens` | 模型输出 Token 数量 |
| `duration_ms` | 完整运行耗时 |
| `error_code` | 失败类型编码 |
| `error_message` | 可直接展示的失败原因 |

## 5. 运行产物字段

`GET /api/runs/{run_id}/artifacts` 在运行过程中也可以调用，只返回已经存在的文件。

| 字段 | 中文含义 | 对应文件 |
|---|---|---|
| `baseline_test` | 修改前测试结果 | `baseline-test.json` |
| `verification_tests` | 每轮修改后的测试结果 | `test-<轮次>.json` |
| `agent_traces` | 每个智能体的输出、工具调用和用量 | `<agent>-<轮次>.json` |
| `evaluation` | 最终测试和审查摘要 | `evaluation.json` |
| `patch` | 标准 Git Patch | `result.patch` |
| `experience` | 失败运行生成的经验 | `experience.json` |
| `metrics` | 版本、Token、耗时和经验指标 | `run-metrics.json` |

## 6. 本地启动

终端一：

```bash
docker compose up -d --wait postgres
docker build -t evodev-python:3.13 sandbox
uv run evodev serve
```

终端二：

```bash
cd frontend
npm install
npm run dev
```

浏览器访问 `http://127.0.0.1:5173`。前端开发服务器会把 `/api` 请求代理到
`http://127.0.0.1:8000`。

## 7. 自动化验收

后端端到端测试使用模拟工作流，避免测试过程产生真实模型费用，同时覆盖完整接口链路：

```text
创建任务
→ 创建后台运行
→ 接收节点状态
→ 查询运行终态
→ 查询测试和补丁产物
```

执行命令：

```bash
uv run pytest
EVODEV_TEST_DATABASE_URL=postgresql://evodev:evodev@localhost:55432/evodev \
  uv run pytest tests/test_postgres_integration.py
cd frontend
npm run lint
npm run test
npm run build
```

浏览器人工检查覆盖普通桌面视口和移动端断点。检查结果包括：中文文案、表单可读性、输入
焦点、按钮对比度、空状态、侧栏收起、指标与工作流响应式排列，以及长标题和代码内容的
溢出处理。

明亮主题的默认任务页通过 Lighthouse 检查：Performance、Accessibility 和 Best Practices
均为 100 分，LCP 为 1.4 秒，CLS 为 0，TBT 为 0 毫秒，浏览器控制台无报错。该结果基于
本地 PostgreSQL、后端接口和前端生产预览全部正常运行时测得。
