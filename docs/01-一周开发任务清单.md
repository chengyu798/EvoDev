### 文档命名约定

`docs` 目录中的文档统一使用以下命名方式：

```text
两位数编号-简单直白的中文名称.md
```

例如：

```text
01-一周开发任务清单.md
02-系统架构设计.md
03-接口设计.md
```

新文档按编号顺序递增，不重复使用已有编号。

## 2. 一周版本目标

EvoDev 首版定位为：

> 一个基于 LangGraph 的多智能体软件修复系统，能够在 Docker 沙箱中由 Analyst、Developer、Reviewer 等 Agent 协作分析代码仓库、生成补丁、执行测试并迭代修复；系统记录完整执行轨迹，并通过“失败反思—经验提取—经验复用”改进后续任务表现。

本周的核心目标是：

```text
可靠的软件修复闭环
        +
最小经验进化能力
        +
可视化运行证据
```

## 7. 实验指标

使用 5 至 10 个小型 Bug 任务对比：

```text
Baseline
vs.
Baseline + Experience
```

仅记录真实运行结果，不填写预设成绩。

- [ ] Task Success Rate
- [ ] Test Pass Rate
- [ ] Average Retry
- [ ] Token Usage
- [ ] Execution Time

## 8. 范围控制规则

1. 9 月 1 日后不再添加与核心闭环无关的功能。
2. 新需求必须先判断是否影响 9 月 5 日代码冻结。
3. 优先保证任务闭环可运行，其次才是界面和扩展功能。
4. 不为了“多智能体”而将确定性操作强行实现为 Agent。
5. 不为了“自进化”而伪造实验数据或夸大已实现能力。
6. 每个功能必须有可执行证据、测试证据或演示证据。
